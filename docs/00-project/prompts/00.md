# Phase 00: Environment Setup, Tooling & Core Architectural Guardrails (v2.1)

## 1. Objective
Initialize the Laravel 13 application framework, install FilamentPHP v5, integrate essential supporting packages (QR generating, PDF manifests, testing engines, and code-styling formatters), and configure the initial local server environment. 

Additionally, this document establishes **10 Core Architectural Guardrails** derived from a rigorous technical audit. These guardrails represent mandatory implementation rules that your downstream AI code generator **must enforce across all subsequent phases (Phases 01 to 14)** to prevent stock inventory leakage, race conditions, precision issues, and security bypasses.

## 3. Mandatory Architectural Guardrails (Phases 01–14)

All code written by downstream AI processes in subsequent phases **must comply strictly** with the following technical guardrails to avoid logic errors, concurrency collisions, and security loopholes.

### Guardrail 1: Price and Cost Precision Schema (Phase 01 & 06)
*   **The Problem**: Representing unit pricing for tiny items (e.g., single grams of raw coffee beans or milliliters) using `decimal(10,2)` causes rounding truncation. Pricing $0.015 per gram is impossible, producing massive cascading financial errors.
*   **The Guardrail**: All database fields representing variant costs, selling prices, or financial losses must use high-precision decimals (`decimal(12,4)` or `decimal(15,6)`). Restrict two-decimal-place rounding strictly to UI presentation.

### Guardrail 2: Concurrency & `firstOrCreate` Race Conditions (Phase 01 & 04)
*   **The Problem**: In high-concurrency environments, double execution of `firstOrCreate` inside database transactions can lead to duplicate primary/unique key insert collisions and unhandled query exceptions.
*   **The Guardrail**: Wrap the initial `firstOrCreate` statement in `InventoryService::recordMovement` inside a try-catch block. On catching a duplicate entry database exception, fallback to executing a direct database row retrieval to ensure concurrency resilience.
    ```php
    try {
        $stock = WarehouseStock::firstOrCreate(
            ['variant_id' => $variantId, 'warehouse_id' => $warehouseId],
            ['on_hand_quantity' => 0, 'reserved_quantity' => 0]
        );
    } catch (\Illuminate\Database\QueryException $e) {
        $stock = WarehouseStock::where('variant_id', $variantId)
            ->where('warehouse_id', $warehouseId)
            ->firstOrFail();
    }
    ```

### Guardrail 3: Safe Requisition Soft-Deletes & Stock Reservations (Phase 02 & 11)
*   **The Problem**: Enabling `SoftDeletes` on a `TransferRequisition` allows records to be hidden from the table view, but the allocated physical `reserved_quantity` is never decremented on the source warehouse stock, permanently leaking reservations.
*   **The Guardrail**: Register an Eloquent Model Observer or boot listener. Whenever a `TransferRequisition` is soft-deleted, automatically verify if its status is `confirmed` or `dispatched`. If true, iterate through its items, decrement the allocated `reserved_quantity` from the source warehouse, and close corresponding in-transit trackers.

### Guardrail 4: The Substitute Variant Fulfillment Resolution (Phase 04, 07 & 09)
*   **The Problem**: If managers agree on a `substitute_variant_id` during negotiation, but dispatch or receiving logic is hardcoded to target the original `variant_id`, stock calculations are applied to the wrong item.
*   **The Guardrail**: `InventoryService::dispatchTransfer()` and `InventoryService::scanToReceive()` must dynamically resolve the target variant ID at the start of their processing loops:
    ```php
    $actualVariantId = $item->substitute_variant_id ?? $item->variant_id;
    ```
    All subsequent inventory actions (deductions, updates, reservations, and ledger records) must apply to `$actualVariantId`.

### Guardrail 5: Validation Against Negative Quantities (Phase 04 & 07)
*   **The Problem**: Malicious or poorly formatted requests containing negative numbers can bypass calculations, artificially inflating stock parameters or bypassing validation rules.
*   **The Guardrail**: Apply strict validation assertions on the API/service layer. Ensure `lockStockForRequisition` and `dispatchTransfer` explicitly require requested/approved base unit quantities to be greater than zero.

### Guardrail 6: Scanned Receipt Loss Integrity & Omitted Items (Phase 04 & 09)
*   **The Problem**: In `InventoryService::scanToReceive()`, skipping expected items that are absent in the scan payload leaves those items indefinitely in the `InTransit` bucket without recording any financial loss.
*   **The Guardrail**: Do not skip omitted elements. If a dispatched item is completely missing from the scanned intake dataset, treat it as receiving `good_qty = 0` and `damaged_qty = 0`. Compute a 100% variance loss, write the discrepancy to the `LossLedger`, and resolve/clear the transit record.

### Guardrail 7: Signed Route Error Interception (Phase 08)
*   **The Problem**: Expired or unauthorized signed URL scans render raw Laravel `403 Invalid Signature` pages, which frustrates warehouse staff scanning physical sheets.
*   **The Guardrail**: Build custom routing verification logic instead of placing Laravel's default `signed` middleware directly on the route. Intercept signature validation failures and redirect users back to their dashboard with an explicit Filament warning banner.

### Guardrail 8: High-Performance Widget Caching (Phase 13)
*   **The Problem**: Aggregating `sum()` metrics across massive tables like `WarehouseStock` and `InTransit` on every page refresh will slow down the central dashboard under scaling.
*   **The Guardrail**: Wrap heavy widget sum calculations (e.g., in `InventoryStatsWidget.php`) in short-term cache tags (e.g., using `Cache::remember` with a 5-minute TTL) to maintain high-performance load times.

### Guardrail 10: CI/CD Testing Database Isolation (Phase 14)
*   **The Problem**: Running unit tests alongside headless browser E2E workflows concurrently against the same testing database leads to race conditions and false test failures due to data state contamination.
*   **The Guardrail**: In `.github/workflows/ci.yml`, isolate standard Pest unit testing by executing against an in-memory SQLite database (`:memory:`). The PostgreSQL container database should be reserved exclusively for sequential headless browser Dusk/Playwright workflow runs.
